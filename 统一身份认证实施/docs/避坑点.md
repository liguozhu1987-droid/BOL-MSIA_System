## 1. TLS 与主机名

### 1.1 HSTS 会让同一主机名的所有明文端口打不开

**现象**：在浏览器访问过 `https://iame.ap.inalfa.local:8443` 之后，`http://iame.ap.inalfa.local:8078` 报 `ERR_SSL_PROTOCOL_ERROR`；换隐私窗口、清浏览器记录都无效；而在服务器上 `Invoke-WebRequest http://iame.ap.inalfa.local:8078/...` 返回 200。

**根因**：Keycloak 返回 `Strict-Transport-Security: max-age=31536000; includeSubDomains`。HSTS **以主机名为键、忽略端口**——浏览器此后把该主机名的**任何端口**都先按 https 发起握手，命中明文端口即握手失败。清记录无效，是因为登录必经 8443，一登录就把 HSTS 重新写回。

**正确做法**：同一主机名只能全 https，或让明文端口换一个主机名。方案 2 就是前者：三个应用全部经 IIS 以 https 暴露，应用侧只在回环上跑明文。

**判据**：`curl.exe -s -o NUL -w "%{http_code}" http://iame.ap.inalfa.local:8078/` 返回 200（curl 不读 HSTS），而浏览器同一 URL 失败 —— 两者不一致即确认为 HSTS，不是服务端问题。落地后浏览器里不应再出现任何 `http://iame.ap.inalfa.local` 的入口（详见 `keycloak-domain-cutover-step-by-step.md` 0.6）。

### 1.2 `netsh http show sslcert` 过滤无输出，不代表证书没绑

**现象**：`netsh http show sslcert | Select-String ':8078'` 无输出，据此判定「证书没绑上」，实际浏览器访问正常。

**根因**：`show sslcert` 的输出里，普通绑定是 `IP:port`、SNI 绑定是 `Hostname:port`，两种栏目格式不同；再加过滤串写法（大小写、是否带主机名）稍有出入就匹配不到。过滤结果为空只说明"没匹配到这一行"，不说明"没有这个绑定"。

**正确做法**：判定证书绑定与证书链是否有效，用一次真实的 HTTPS 请求——`Invoke-WebRequest` 默认校验证书链，能返回 200 就说明绑定、SNI、证书链三者都对。

**判据**：

```powershell
(Invoke-WebRequest 'https://iame.ap.inalfa.local:8078/api/auth/config' -UseBasicParsing).StatusCode   # 期望 200
netsh http show sslcert | Select-String 'iame.ap.inalfa.local'   # 只作旁证，不作判据
```

### 1.3 `keycloak.conf` 里的 keystore 口令与实际值不一致 → 17 秒重启循环

**现象**：Keycloak 服务起不来，日志只有一行致命错误，服务状态反复在 `Running` / `Stopped` 之间跳；按时间戳量约**每 17 秒重启一次**。

```text
java.io.IOException: keystore password was incorrect
```

**根因**：`keycloak.conf` 里 `https-key-store-password` 写进去的值与 `C:\certs\iame.p12` 的真实口令不一致。NSSM 的 `AppExit=Restart` 把每次启动失败都自动拉起，于是变成稳定的重启循环；日志被反复覆盖，很容易只看到"服务在跑"而漏掉退出原因。

**正确做法**：

1. 先**独立验证** keystore 真实口令，不要用 `keycloak.conf` 里的值自证：

```powershell
keytool -list -keystore C:\certs\iame.p12 -storetype PKCS12
```

2. 口令确认后，用 `Read-Host` 取值并按**字面量**重写该行：

```powershell
$pw = Read-Host 'keystore password'
$conf = 'C:\keycloak\conf\keycloak.conf'
$lines = Get-Content $conf -Encoding UTF8 | ForEach-Object {
    if ($_ -match '^\s*https-key-store-password\s*=') { "https-key-store-password=$pw" } else { $_ }
}
[IO.File]::WriteAllText($conf, ($lines -join "`r`n"), (New-Object System.Text.UTF8Encoding($false)))
```

**不要用双引号拼字符串写这一行**：口令里出现 `$`、反引号、`#` 时，双引号写法会被 PowerShell 插值或提前截断（`#` 之后被当注释），写进文件的就不是原口令——这正是本次重启循环的来源。同样不要用 `Get-Content | Set-Content` 回写（见 4.1）。

**判据**：`keytool -list` 用同一口令能列出条目；重启后服务连续 1 分钟保持 `Running`，日志中不再出现 `keystore password was incorrect`；`https://iame.ap.inalfa.local:8443/realms/master` 能返回 JSON（证书 `CN=iame.ap.inalfa.local`，签发者 `CN=ap-SRV-APSH-PKI-01-CA-1`，到期 2028-07-31）。

## 2. IIS 反向代理

### 2.1 `allowedServerVariables` 属于 URL Rewrite，不在 `proxy` 下

**现象**：按「往 `proxy` 段加集合」的思路配置转发头白名单，各种写法都失败或静默不生效。

**根因**：路径归属搞错。`applicationHost.config` 里 `allowedServerVariables` 在 `sectionGroup name="rewrite"` 内，完整路径是 `system.webServer/rewrite/allowedServerVariables`；`system.webServer` 组下只有 `proxy`（`overrideModeDefault="Deny"`、`allowDefinition="AppHostOnly"`）与 `diskCache` 两个 section。写到 `proxy` 上会被当成未知属性/未知子节点。

**正确做法**：只用 `Add-WebConfiguration` 加，`appcmd` 只用来回读。

```powershell
Import-Module WebAdministration
Add-WebConfiguration -PSPath 'MACHINE/WEBROOT/APPHOST' `
    -Filter 'system.webServer/rewrite/allowedServerVariables' -Value @{name='HTTP_X_FORWARDED_PROTO'}
Add-WebConfiguration -PSPath 'MACHINE/WEBROOT/APPHOST' `
    -Filter 'system.webServer/rewrite/allowedServerVariables' -Value @{name='HTTP_X_FORWARDED_FOR'}
```

失败特征对照（见到即说明写法错了）：

| 写法 | 结果 |
|---|---|
| `appcmd set config /section:system.webServer/proxy "/+[name='HTTP_X_FORWARDED_PROTO']"` | `Unknown attribute "[name='HTTP_X_FORWARDED_PROTO']"` |
| `Add-WebConfigurationProperty -Filter 'system.webServer/proxy' -Name 'allowedServerVariables'` | `Property allowedServerVariables is not found on system.webServer/proxy` |
| `-Filter 'system.webServer/proxy/allowedServerVariables'` | 不报错、**静默不生效** |
| `appcmd list config /section:system.webServer/allowedServerVariables` | `Unknown config section` |

**判据**：

```powershell
& "$env:SystemRoot\System32\inetsrv\appcmd.exe" list config /section:system.webServer/rewrite/allowedServerVariables
```

回读含 `<rewrite><allowedServerVariables><add name="HTTP_X_FORWARDED_PROTO" />…` 即成功，**但条数必须与 `<set>` 的条数一致**（漏一条的表现见 2.5）。节路径不明时：`Select-String -Path "$env:SystemRoot\System32\inetsrv\config\applicationHost.config" -Pattern '<节名>' -Context 8, 8`，向上最近的 `sectionGroup name="..."` 就是归属（完整枚举写法见 `iis-arr-precheck.md` 4.5.1）。

### 2.2 ARR 装没装，不能看 `inetsrv\requestRouter.dll`

**现象**：`C:\Windows\System32\inetsrv\requestRouter.dll` 不存在，据此判定 ARR 没装上；实际 ARR 早已装好、代理也在工作。

**根因**：ARR 的模块文件落在 **`C:\Program Files\IIS\Application Request Routing\`**，不在 `inetsrv`。查错位置把"已装好"误判成"没装"（URL Rewrite 的 `rewrite.dll` 才在 `inetsrv` 下，两者不同）。

**正确做法**：三条合并判定，缺一不算装成。

```powershell
Get-ChildItem 'C:\Program Files\IIS\Application Request Routing' -Filter 'requestRouter.dll' -Recurse -ErrorAction SilentlyContinue
Import-Module WebAdministration
Get-WebGlobalModule | Where-Object { $_.Name -match 'ApplicationRequestRouting' } | Select-Object Name, Image
& "$env:SystemRoot\System32\inetsrv\appcmd.exe" list config /section:system.webServer/proxy
```

**判据**：目录下有 `requestRouter.dll`、全局模块出现 `ApplicationRequestRouting`、`proxy` 节能被读出（能返回即说明 ARR 生效，`enabled` 默认 `false`）。

### 2.3 静默安装会把回滚藏起来

**现象**：`Start-Process msiexec.exe -ArgumentList '/i ... /qn /norestart' -Wait` 跑完屏幕上只有新提示符，看起来装完了，实际什么都没装（ARR 因 IIS 未装而整包回滚，文件不落地、卸载表无记录）。

**根因**：`-Wait` 只等进程退出，**不传递结果**；`/qn` 又把所有提示吞掉，MSI 在后台完成了「检测前置 → 失败 → 回滚 → 删文件 → 清注册表」全程而无人知晓。

**正确做法**：固定写法（`-PassThru` 取退出码 + `/l*v` 落日志），并且安装顺序必须是 **IIS → URL Rewrite → `iisreset` → ARR**（URL Rewrite 依赖 IIS 注册模块，ARR 依赖 URL Rewrite）。

```powershell
$log = 'C:\Temp\iis-setup\arr-install.log'
$p = Start-Process msiexec.exe `
        -ArgumentList "/i C:\Temp\iis-setup\requestRouter_amd64.msi /qn /norestart /l*v `"$log`"" `
        -Wait -PassThru
"ExitCode = $($p.ExitCode)"
Select-String -Path $log -Pattern 'Return value 3|LaunchCondition|Installation failed'
```

- 退出码：`0` 成功；`3010` 成功但需重启（不当失败重装）；`1603` 安装过程中致命错误，唯一可查处是日志；`1602` 中止；`1618` 另一个安装正在进行。
- 日志关键字：`Return value 3`（3 = 该动作失败并回滚，**紧邻上方几行**就是失败的那一步）、`LaunchCondition`（前置不满足，最常见是 IIS 未装）、`Installation failed`（整包回滚）。

**判据**：每条 MSI 都以「退出码 + 对应 2.2 的三条」判定，不以"命令没报错"判定。`Get-WindowsFeature Web-Server` 的 `InstallState` 出现 `Available` 就是**未安装**——这是本次 ARR 失败的真正根因。

### 2.4 IIS 站点无法与 `0.0.0.0:<端口>` 共用端口

**现象**：应用监听 `0.0.0.0:8078`，IIS 站点也绑 `8078`，站点起不来或被绕过，请求仍直达应用。

**根因**：`0.0.0.0` 覆盖本机全部地址，该端口已被应用独占，IIS（`http.sys`）抢不到监听；此时"配了反代"只是表面现象。

**正确做法**：先让应用只绑回环（`127.0.0.1`），IIS 再绑对外地址/主机名。三个应用的落点不同：MSIA 改 `config.ini` 的 `[server]`、BOL 改 NSSM `AppParameters`、**Capacity 的监听地址写死在程序内**（`nssm get CapacityAPI AppParameters` 为空，`.env` 里没有 `HOST`/`PORT`/`BIND`/`SERVER_HOST`/`LISTEN`），实测 `HOST=127.0.0.1` 未被采用，只能走公网换端口（8008，见 2.6–2.8）。

**判据**：

```powershell
Get-NetTCPConnection -LocalPort 8078,8090,8000 -State Listen | Select-Object LocalAddress, LocalPort, OwningProcess
```

`LocalAddress` 为 `127.0.0.1` 才算改绑成功；仍为 `0.0.0.0` 就必须走换端口那条路。现场 Capacity 实测 `HOST=127.0.0.1` 未被采用，已按公网 8008 落地并验证登录；8000 的对外阻断本次决定不做，`http://172.26.2.203:8000/...` 旧 URI 必须保留（处置见 `plan-b-https-cutover-playbook.md` C2.3，封口方法见 2.8）。

### 2.5 `500.50` 全是白名单漏登记，不是应用或证书问题

**现象**：三个反代站点同时报 `HTTP Error 500.50 - URL Rewrite Module Error`，正文为 `The server variable "HTTP_X_FORWARDED_FOR" is not allowed to be set.`，`Error Code 0x80070005`，IIS 日志 `sc-status=500 sc-substatus=50 sc-win32-status=5`；而直连后端 `http://127.0.0.1:8078/api/auth/config`、`:8090/api/auth/config` 都是 200。

**根因**：`web.config` 的 `<serverVariables>` 里 `<set>` 了两个变量（`HTTP_X_FORWARDED_PROTO`、`HTTP_X_FORWARDED_FOR`），而 `system.webServer/rewrite/allowedServerVariables` 只登记了前者。

**规则**：**`<set>` 里出现几个变量名，白名单就必须登记几条，一个不能少**。漏一条就是整站 500.50——因为 rewrite 规则对所有路径生效，不会只有某个路径坏。只有 rewrite 的 `<set>` 需要登记；ARR 自己自动追加的 `X-Forwarded-For` 不受此限制。

**正确做法**：补齐缺的那条，**改完立即生效，不需要 `iisreset`**。

```powershell
Import-Module WebAdministration
Add-WebConfiguration -PSPath 'MACHINE/WEBROOT/APPHOST' `
    -Filter 'system.webServer/rewrite/allowedServerVariables' -Value @{name='HTTP_X_FORWARDED_FOR'}
```

**判据**：回读条目数等于 `<set>` 的条数（现场为 2）。

```powershell
& "$env:SystemRoot\System32\inetsrv\appcmd.exe" list config /section:system.webServer/rewrite/allowedServerVariables
Select-String -Path 'C:\inetpub\proxy\*\web.config' -Pattern '<set name=' | Select-Object Path, Line
```

**判读提醒**：只看到 `500` 定位不了问题，必须取子状态码与正文——`500.19` 是配置锁（节被锁/白名单缺失导致 web.config 无法解析）、`500.50` 是 rewrite **运行期**失败、`500.100` 是脚本错误。

```powershell
try { Invoke-WebRequest 'https://iame.ap.inalfa.local:18078/api/auth/config' -UseBasicParsing }
catch { [int]$_.Exception.Response.StatusCode; $_.ErrorDetails.Message }
```

### 2.6 `New-WebBinding` 报 `duplicate collection entry` 不是失败

**现象**：执行 `New-WebBinding -Name 'IAME-CAPACITY' -Protocol https -Port 8008 ...`，报 `Cannot add duplicate collection entry of type 'binding' with unique key attribute 'protocol', 'bindingInformation'`，被当成绑定没加上。

**根因**：这条绑定已经在。`binding` 集合以 `protocol` + `bindingInformation`（IP:port:hostheader）为唯一键，重复添加必然报这个错，与"配置出错"无关。

**正确做法**：看到这个错就停手，不删不重建，直接用 `Get-WebBinding` 回读确认条数与内容。

```powershell
Get-WebBinding -Name 'IAME-CAPACITY' -Protocol https | Select-Object BindingInformation, Port
```

**判据**：回读中出现 `*:8008:iame.ap.inalfa.local` 即满足；条目数与预期一致（现场为 8008 与 18000 各一条）就不要再加。

### 2.7 `New-WebBinding` 只加站点绑定，不给新端口挂证书

**现象**：`New-WebBinding` 成功、`Get-WebBinding` 能看到 `*:8008`，但访问 `https://iame.ap.inalfa.local:8008/health` 直接 TLS 握手失败（`curl -k` 报 `SSL_ERROR_SYSCALL`、浏览器报 `ERR_SSL_PROTOCOL_ERROR`），**不是 502/503**。

**根因**：`New-WebBinding` / `Set-WebBinding` 只改站点绑定（protocol / ip / port / hostheader），不碰 `http.sys` 的 SSL 证书表。新端口没有 `sslcert` 条目，TLS 在握手阶段就断，请求根本没进 IIS 管道，所以不会出现 503。

**正确做法**：每个新端口单独 `netsh http add sslcert`，Application ID 沿用同站点已有端口那条的 GUID（同一站点多端口共用一个 appid，便于统一删除）。

```powershell
netsh http show sslcert | Select-String '18000' -Context 0,5    # 取现成的 Guid
netsh http add sslcert ipport=0.0.0.0:8008 `
    certhash=A1FC2947BADE887B00E6C0BF4CC0E6FA7D59AC0A `
    appid='{4dc3e181-e14b-4a21-b022-59fc669b0914}' certstorename=MY
```

**判据**：`https://iame.ap.inalfa.local:8008/health` 返回 200。用 `Invoke-WebRequest` 而非 `-k`，能 200 就说明绑定、SNI、证书链三者都对。

### 2.8 Windows 防火墙 Block 优先于 Allow，回环也照封

**现象**：按"先允许回环、再全封"的思路配置，先加 `127.0.0.1` 的 Allow 再加 `LocalPort=8000` 的 Block，结果 IIS 反代也 502；反过来，只加 Allow 又封不住外部。

**根因**：Windows 防火墙按 **Block > Allow** 的优先级匹配，与规则创建顺序无关。一条命中端口的 Block 会盖住任何更细的 Allow（包括地址限定的那条），所以"先允许回环再全封"必然把回环一起封掉；而回环流量走本机协议栈内部，**不经过**防火墙入站筛选，本来就不需要放行。

**正确做法**：不写回环 Allow，直接一条对目标端口全封，封完用回环地址回读。

```powershell
# 规则名按现场命名风格自定，此处仅示意；放行规则现场名为 IAME-CAPACITY-HTTPS-8008
New-NetFirewallRule -DisplayName '<阻断规则的名称>' -Direction Inbound `
    -Action Block -Protocol TCP -LocalPort 8000 -Profile Domain,Private,Public
"127 CAP " + (curl.exe -s -o NUL -w "%{http_code}`n" "http://127.0.0.1:8000/health")
```

**判据**：回读 `http://127.0.0.1:<端口>/health` 为 `200`；不是 200 立即 `Remove-NetFirewallRule -DisplayName '<同一名称>'` 回退。外部是否真被封，只能从另一台机器访问判定，本机回读不能自证。

### 2.9 预演绑定会占住应用要用的内部端口

**现象**：按 5.1 建的预演站点把 `18090` 绑在自己身上（`https *:18090`）。随后改 BOL 服务参数为 `BOLServer.exe --port 18090`，服务启动后立刻退出，`Get-Service BOL-Server` 显示 `Stopped`，日志没有应用层报错——端口根本轮不到应用去绑。

**根因**：IIS 的 `https` 绑定落在 HTTP.sys 上，`*:18090` 是全地址监听。应用随后 `bind(127.0.0.1:18090)` 时端口已被 HTTP.sys 独占（与 2.4 同一机制，只是这次占用方是 IIS 预演站点，不是生产应用），绑定失败即退出。

**正确做法**：切正式端口之前，先删掉占着内部端口的预演绑定，再启动应用。

```powershell
Import-Module WebAdministration
Get-WebBinding -Name 'IAME-BOL' | Select-Object Protocol, BindingInformation
Remove-WebBinding -Name 'IAME-BOL' -Port 18090
Get-NetTCPConnection -LocalPort 18090 -State Listen -ErrorAction SilentlyContinue   # 应无输出
```

顺序固定为：**删预演绑定（内部端口）→ 起应用 → 正式端口加绑定并挂证书**。三个应用同理（18078 / 18090 / 18000 这三个内部端口都要先腾空）。

**判据**：删绑定后 `Get-NetTCPConnection -LocalPort <内部端口> -State Listen` 无输出；启动应用后该端口 `Listen` 的 `OwningProcess` 是应用自己的 PID（不是 `System`/`PID 4`），且回环探针返回 200：

```powershell
(Invoke-WebRequest 'http://127.0.0.1:18090/' -UseBasicParsing -TimeoutSec 15).StatusCode   # 期望 200
```

## 3. 应用侧

### 3.1 waitress 3.x 默认会剥掉转发头

**现象**：经 IIS 反代后，登录流程能走完，但登录后**所有 POST 都 403**（Django `CSRF verification failed`），日志里没有任何证书或网络错误。

**根因**：waitress 3.x 默认 `clear_untrusted_proxy_headers=True`。没有声明 `trusted_proxy` 时，`X-Forwarded-Proto` 在进 Django **之前**就被丢弃，`SECURE_PROXY_SSL_HEADER` 永远读不到，Django 认为请求是 http、Origin 是 https，CSRF 校验不通过。

**正确做法**：两处同时到位。

```python
# BOL 启动 waitress 的地方
serve(app, host='127.0.0.1', port=8090,
      trusted_proxy='127.0.0.1',
      trusted_proxy_headers={'x-forwarded-proto'})
```

- IIS 侧 `web.config` 必须写 `<set name="HTTP_X_FORWARDED_PROTO" value="https" />`，且该变量要先进 `allowedServerVariables` 白名单（见 2.1）；
- **反代上游必须写 `127.0.0.1`**：写 `localhost` 或服务器 IP 都匹配不上 `trusted_proxy`，该头照样被丢弃，症状与完全没改代码一模一样。

**判据**：BOL 业务页做一次「新增/保存」不出现 `CSRF verification failed`；或临时在视图里打印 `request.META.get('HTTP_X_FORWARDED_PROTO')`，应为 `https`。

### 3.2 Capacity 的探针端点只有 `/health` 可用

**现象**：用 `/docs`、`/openapi.json`、`/api/v1/health` 做健康探针全部 404，被判成 FAIL；其中 `/api/v1/health` 返回 `{"detail":"Not Found"}`。

**根因**：该应用没有暴露 OpenAPI 文档，也没有 `/api/v1/health` 这个路由；`{"detail":"Not Found"}` 是 FastAPI 自己返回的 JSON，恰恰说明请求已经穿过 ARR 到达应用——是链路通的旁证。

**正确做法**：探针一律用 `/health`。`register-services-nssm.ps1` 里 Capacity 的探针需相应改成 `/health`。

**判据**：

```powershell
curl.exe -k -s -o NUL -w "%{http_code}`n" 'https://iame.ap.inalfa.local:8008/health'   # 期望 200
curl.exe -k -s -o NUL -w "%{http_code}`n" 'https://iame.ap.inalfa.local:8008/'         # 期望 200（页面）
```

### 3.3 MSIA 自有校验：`issuer` 与 `redirect_uri` 主机名必须一致

**现象**：MSIA 配置为 `issuer` 指 IP、`redirect_uri` 指域名时，登录失败，日志给出：

```text
OIDC 配置不完整: oidc.issuer 主机名 (172.26.2.203) 与 oidc.redirect_uri 主机名 (iame.ap.inalfa.local) 不一致
```

错误发生在应用启动后首次 OIDC 调用，浏览器侧只看到登录不可用。

**根因**：这是 MSIA **应用自身**的前置校验，不是 Keycloak、证书或网络问题。只要两个 URL 的主机名不同就直接拒绝。

**正确做法**：把 `issuer` 与 `redirect_uri` 放在同一批次改成同一主机名，并与 Keycloak 切域名同窗口；不要单独切某一个应用（2026-11-11 已因此回退 MSIA）。

**判据**：

```powershell
(Select-String -Path 'C:\ApplicationFile\ExecuteProgram\msia_sever\msia_server\config.ini' -Pattern '^\s*(issuer|redirect_uri)\s*=').Line
```

两者主机名相同（都是 IP 或都是 `iame.ap.inalfa.local`）才算合格。误判方向是"Keycloak 坏了"，实际不涉及 Keycloak 连通性。

### 3.4 `SSL_CERT_FILE` 的 bundle 要含服务端证书；切正式证书后要追加整条链

**现象**：Python 应用日志报

```text
OIDC discovery 拉取失败：[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate
idp_unreachable
```

浏览器侧只看到"统一身份认证服务暂不可用"，不出现证书告警。

**根因**：应用的 `SSL_CERT_FILE` 指向 `C:\certs\ca-bundle.pem`，但该 bundle 里没有 Keycloak 当前使用的服务端证书（自签阶段是 `C:\keycloak\conf\server.crt.pem`），Python 侧校验链断开。`SSL_CERT_FILE` 是**替换**系统默认信任集，不是追加。

**正确做法（现场做法）**：把 `C:\certs\iame-all.pem`（**叶 + 中间 + 根**）追加进 `C:\certs\ca-bundle.pem`，证书块由 3 变 6；三个应用统一用 `SSL_CERT_FILE=C:\certs\ca-bundle.pem`。

```powershell
$b = 'C:\certs\ca-bundle.pem'
"before=" + ([regex]::Matches((Get-Content $b -Raw), '-----BEGIN CERTIFICATE-----')).Count
Add-Content -Path $b -Value (Get-Content 'C:\certs\iame-all.pem' -Raw) -Encoding ASCII
"after="  + ([regex]::Matches((Get-Content $b -Raw), '-----BEGIN CERTIFICATE-----')).Count
```

三点必须注意：

- 正式证书校验的是**签发根 CA**（现场 `CN=ap-SRV-APSH-PKI-01-CA-1`），只追加叶子证书不够，同症状会换个原因复现；`iame-all.pem` 一次带全叶/中间/根，比逐张追加省事。
- **BOL 原本指向 `C:\keycloak\conf\server.crt.pem`（旧自签）**，切正式证书时必须改到 `ca-bundle.pem`，否则它仍只信旧自签证书。改 NSSM：`AppEnvironmentExtra="SSL_CERT_FILE=C:\certs\ca-bundle.pem"`。
- 追加前先备份（现场保留 `ca-bundle.pem.bak` / `.bak2` 一周）。

**判据**：`before=3`、`after=6`；三个应用重启后日志无 `CERTIFICATE_VERIFY_FAILED` / `idp_unreachable`，三条登录链路（8078 / 8090 / 8008）都能走完。

### 3.5 BOL 的端口与主机在 NSSM `AppParameters`，不在 `db_config.ini`

**现象**：为了让 BOL 只绑回环，翻 `db_config.ini` 找 `[server]` 段或 `host` / `port` 键，找不到，误以为"BOL 端口写死、改不了"。

**根因**：`BOLServer.exe` 的监听参数是**命令行参数**（`--host` / `--port`，`README_DEPLOY.txt` 有写明），由 NSSM 的 `AppParameters` 传入；`db_config.ini` 里只有数据库与 OIDC 配置，**没有 `[server]` 段**。

**正确做法**：改 NSSM 参数后重启服务。

```powershell
$nssm = (Get-CimInstance Win32_Service -Filter "Name='BOL-Server'").PathName -replace '^"([^"]+)".*$', '$1'
& $nssm set BOL-Server AppParameters '--host 127.0.0.1 --port 18090'
& $nssm set BOL-Server AppEnvironmentExtra 'SSL_CERT_FILE=C:\certs\ca-bundle.pem'
Restart-Service BOL-Server
```

**判据**：`Get-NetTCPConnection -LocalPort 18090 -State Listen` 的 `LocalAddress` 为 `127.0.0.1`；`http://127.0.0.1:18090/` 返回 200；`https://iame.ap.inalfa.local:8090/` 登录链路通过。注意 18090 先按 2.9 腾空，否则服务起不来。

## 4. PowerShell / 运维命令

### 4.1 PS 5.1 读 UTF-8 文件必须带 `-Encoding UTF8`

**现象**：读 `.env` 出来是乱码；更隐蔽的是**行被错并**——本次实测 `DB_HOST=` 被并进了上一行注释，看起来"这个键不存在"，据此做判断就会得出错误结论。

**根因**：Windows PowerShell 5.1 的 `Get-Content` 对**无 BOM 的 UTF-8** 按 ANSI（GBK）解码，多字节字符被拆错后换行位置也跟着错位。

**正确做法**：读一律带 `-Encoding UTF8`；写用 `[IO.File]::WriteAllText` + `UTF8Encoding($false)`（不加 BOM），**严禁 `Get-Content | Set-Content` 管道回写**（会同时引入乱码与 BOM）。

```powershell
$p = 'C:\ApplicationFile\ExecuteProgram\Capacity\publish\.env'
Get-Content $p -Encoding UTF8 | Select-String '^\s*OIDC_ISSUER\s*='
```

**判据**：`(Get-Content $p -Encoding UTF8).Count` 与编辑器行数一致；`Select-String -Encoding UTF8 -Pattern '^DB_HOST='` 能命中；有 BOM 时首行键名前会出现 `\ufeff`（`$bk = (Get-Content -Path $p -Encoding UTF8)[0]; $bk.StartsWith([char]0xFEFF)` 为 `True` 即中招）。

> 另一个同源的坑：PS 5.1 里给 `Invoke-WebRequest` 的 URL **不要用反引号包裹**（如 `` `https://...` ``）。反引号是转义符，其内容会原样进入请求 URI，IIS 错误页的 `Requested URL` 会把这个异常显形，容易被误读成"路径配错"。URL 用单引号包即可。

### 4.2 nssm 不在 PATH 时，从服务登记里取它

**现象**：`nssm` 命令找不到，去全盘搜 `nssm.exe` 又慢又容易拿到旧副本。

**根因**：`nssm` 只是注册服务时用的工具，装完不一定在 `PATH`；但服务本身的 `ImagePath` 就是它的绝对路径。

**正确做法**：

```powershell
(Get-CimInstance Win32_Service -Filter "Name='CapacityAPI'").PathName
```

**判据**：`PathName` 形如 `"D:\tools\nssm\nssm.exe" CapacityAPI`，去掉引号的第一段即 `nssm.exe` 的完整路径；直接用它执行，例如 `& 'D:\tools\nssm\nssm.exe' get CapacityAPI AppParameters`。

### 4.3 反引号包住 URL 只能做字节级检查

**现象**：终端回显或 Markdown 渲染出来是 `` `https://iame.ap.inalfa.local:8008/health` ``，肉眼判断不了文件里到底有没有这对反引号；用 `Select-String` 看也只看到被引号包着的显示结果，据此改文件容易改错或漏改。

**根因**：反引号在 PowerShell 里是转义符、在 Markdown 里是行内代码标记，显示层和复制粘贴都可能添加或吞掉它；`Select-String` 输出的是渲染后的行，不能作为"文件里有无该字符"的证据。

**正确做法**：读原文做字节级判断。

```powershell
$p = 'C:\ApplicationFile\ExecuteProgram\Capacity\publish\.env'
$raw = Get-Content -Path $p -Raw -Encoding UTF8
$raw.Contains([char]96)                                   # True = 文件里确实有反引号
($raw -split "`n") | Where-Object { $_.Contains([char]96) }   # 定位到具体行
```

**判据**：`False` 才算干净；`True` 时按上面第二条输出定位到行，逐字符改掉。这条同样适用于写进 `.env` 的 URL 和传给 `Invoke-WebRequest` 的地址（PS 5.1 的反引号会原样进 URI，见 4.1 末尾）。

### 4.4 `SslStream.AuthenticateAsClient($host)` 单参重载走 TLS 1.0

**现象**：自写的 TLS 探测脚本连 Keycloak 失败，报 `Win32Exception: The function requested was not supported`（`0x80090302`）；同一时间浏览器与 `Invoke-WebRequest` 访问同一地址都是正常的。

**根因**：`SslStream.AuthenticateAsClient($host)` 这个单参重载在 .NET Framework 下**固定用默认 TLS 1.0**，`ServicePointManager.SecurityProtocol` 对它不生效。Keycloak 拒绝 TLS 1.0 后，客户端报的就是上面那个 Win32 错误。

**正确做法**：显式传协议。

```powershell
# 变量名不要用 $host，它是 PowerShell 保留变量
$srv = 'iame.ap.inalfa.local'
$tcp = New-Object System.Net.Sockets.TcpClient
$tcp.Connect($srv, 8443)
$ssl = New-Object System.Net.Security.SslStream($tcp.GetStream(), $false, { $true })
$ssl.AuthenticateAsClient($srv, $null, [System.Security.Authentication.SslProtocols]::Tls12, $false)
$ssl.SslProtocol   # 应为 Tls12
$tcp.Close()
```

**判据**：探测成功且 `SslProtocol` 为 `Tls12`。**不要把"探测脚本不对"误判成"服务端 TLS 坏了"**——先看协议版本，再去查服务端。

**同一个坑的第二面：`ServicePointManager.SecurityProtocol` 管不到 `SslStream`，而且 ServicePoint 会缓存旧协议。**

**现象**：同一个 PowerShell 会话里，先按默认协议连过某个 `host:port`（或因前一次失败留下了会话），之后再 `[Net.ServicePointManager]::SecurityProtocol = 'Tls12'` 重试，仍报 `unexpected error occurred on a send` 一类发送期错误；而新开一个进程做同样的事就是通的。

**根因**：`ServicePointManager.SecurityProtocol` 只作用于 `HttpWebRequest` / `WebClient` 这条栈，对裸 `SslStream` 完全无效；同时 `ServicePoint` 以 `host:port` 为键缓存连接与协商结果，旧协议/旧 TLS 会话会在这个会话里被复用。

**正确做法**：验证服务端一律走裸 TLS + 手工 HTTP，且**换新进程**再设协议。

```powershell
# 变量名不要用 $host（PowerShell 保留变量）
$srv = 'iame.ap.inalfa.local'
$tcp = New-Object System.Net.Sockets.TcpClient
$tcp.Connect($srv, 8443)
$ssl = New-Object System.Net.Security.SslStream($tcp.GetStream(), $false, { $true })
$ssl.AuthenticateAsClient($srv, $null, [System.Security.Authentication.SslProtocols]::Tls12, $false)
$req = "GET /realms/master HTTP/1.1`r`nHost: ${srv}:8443`r`nConnection: close`r`n`r`n"
$buf = [Text.Encoding]::ASCII.GetBytes($req)
$ssl.Write($buf, 0, $buf.Length); $ssl.Flush()
(New-Object IO.StreamReader($ssl)).ReadToEnd() -split "`r`n" | Select-Object -First 1   # 期望 HTTP/1.1 200
$tcp.Close()
```

**判据**：`AuthenticateAsClient` 不抛异常且 `SslProtocol` 为 `Tls12`，手工请求首行为 `HTTP/1.1 200`。若旧会话里反复失败，先确认是不是缓存——**换一个全新的 PowerShell 进程再跑一遍**，能通即证伪"服务端坏了"。

### 4.5 `Get-Process -Id <服务进程>` 查不到不等于进程不存在

**现象**：用服务的 PID 执行 `Get-Process -Id <PID>` 返回"找不到进程"，据此判定 Keycloak 变成僵尸进程并准备重启；实际服务一直正常。

**根因**：NSSM 托管的服务运行在服务会话（Session 0）里，部分情况下当前管理员会话取不到该进程对象，`Get-Process -Id` 直接报不存在。这是**取不到**，不是**没有**。

**正确做法**：判断存活只看服务状态与端口监听。

```powershell
(Get-Service 'Keycloak').Status
Get-NetTCPConnection -LocalPort 8443 -State Listen |
    Select-Object LocalAddress, LocalPort, OwningProcess
```

**判据**：`Status=Running` 且端口处于 `Listen`（`OwningProcess` 可作为旁证）。只要这两条成立，就不要重启服务；需要进程细节时改用 `Get-CimInstance Win32_Process -Filter "ProcessId=<PID>"`。

### 4.6 Keycloak 侧读 broker 令牌报 401：先查会话，别先动开关

**现象**：首次实跑 `scripts/powershell/verify_account_name_claims.ps1`，Keycloak 侧取令牌直接失败，原文：

```
14:40:55 [WARN ] Keycloak 侧取令牌失败：{"error":"HTTP 401 Unauthorized","error_description":"For more on this error consult the server log at the debug level."}
```

**判定**：这是 Keycloak 管理接口返回的 401，不是 OIDC 登录失败，也不是 Store tokens 没开。401 的含义是「token 没通过认证」，只有三种来源：管理员 token 不是该 realm 的有效会话、token 已过期（含主机时间偏差）、token 根本没送到。**权限不足是 403；Store tokens 没开会表现为 404/400，或者在读配置阶段就被拦下。** 所以看到 401 先查会话，不要先去改 IdP 开关。

**排查顺序**（最可能 → 最不可能，均在跑脚本的机器上执行）：

1. 同一个服务端、同一组凭据单独换一次 token。换得到，说明账号本身没问题，问题在 token 的使用方式或 admin 权限：

```powershell
$b=@{grant_type='password';client_id='admin-cli';username='kcadmin';password='<口令>'}
$r=Invoke-RestMethod -Method Post -Uri 'https://iame.ap.inalfa.local:8443/realms/master/protocol/openid-connect/token' -Body $b
$r.expires_in
```

2. 用这个 token 直打一次 admin API，把 200 / 401 / 403 分开：

```powershell
Invoke-RestMethod -Headers @{Authorization="Bearer $($r.access_token)"} 'https://iame.ap.inalfa.local:8443/admin/realms/inalfa'
```

200 = 会话正常，回去看脚本传参（`-AdminRealm` / `-AdminUser` / `-Realm`）；403 = 账号没有该 realm 的管理权限；401 = 继续下一步。

3. 核对时间偏差。Keycloak 主机跑 `w32tm /query /status`，本机跑 `Get-Date`。偏差超过 token 的允许窗口时，刚签发的 token 也会被判无效。

4. kcadm 对照。kcadm 能过、脚本不过，多半是参数传错；kcadm 也 401，说明账号、口令或 realm 有问题：

```powershell
C:\keycloak\bin\kcadm.bat config credentials --server https://iame.ap.inalfa.local:8443 --realm master --user kcadmin
C:\keycloak\bin\kcadm.bat get realms/inalfa
```

5. 账号权限。第 2 步返回 403 时，换 master 超级管理员跑，或在 realm 里赋 `realm-management` 的 `view-users`、`view-identity-providers`。

6. 最后才看 Store tokens / Stored tokens readable。这两个开关没开时的表现是「没有已存储令牌」（404/400），不会报 401。

**脚本侧已改**：`Invoke-Kc` 现在把 HTTP 状态码和请求路径一起抛出；`Get-TokenFromKeycloak` 按状态码归类为 `ADMIN_AUTH`、`ADMIN_UNAUTHORIZED`（401）、`ADMIN_FORBIDDEN`（403）、`IDP_NOT_FOUND`（404）、`USER_NOT_FOUND`、`TOKEN_ABSENT`（400/404）、`STORE_OFF`，并打印「卡在哪一步 + 对应命令」。401 不再只打一条 WARN 就转手工粘贴：交互模式下明确询问，非交互模式直接跳过。

**判据**：第 2 步对 `/admin/realms/inalfa` 返回 200，且脚本重跑能读到 `id_token`。

## 5. 方法论

### 5.1 临时端口预演：把停机窗口压到分钟级

**做法**：在动正式端口之前，先用 **18078 / 18090 / 18000** 另建一套同名站点（`IAME-MSIA` / `IAME-BOL` / `IAME-CAPACITY`），绑定同一个证书与 host header，跑同样一份 `web.config`。这一步完全不碰正式端口与业务，却能把 TLS 终结、证书绑定、rewrite 规则、ARR 总开关、转发头白名单五件事一次性验完。

**收益**：窗口内只剩两件事——C 段的配置切换、站点绑定从临时端口换到正式端口（`Set-WebBinding` + `netsh http add sslcert`），中断时间从"装组件 + 调配置 + 排错"压缩到分钟级；而且任何一环不通过，都在预演阶段暴露，不影响生产。

**判据**（三条全过才算预演通过）：

```powershell
curl.exe -k -s -o NUL -w "%{http_code}`n" 'https://iame.ap.inalfa.local:18078/api/auth/config'   # 200
curl.exe -k -s -o NUL -w "%{http_code}`n" 'https://iame.ap.inalfa.local:18090/api/auth/config'   # 200
curl.exe -k -s -o NUL -w "%{http_code}`n" 'https://iame.ap.inalfa.local:18000/health'            # 200
```

注意端口不同但**主机名相同**，所以 HSTS 不再是问题（见 1.1）；这也说明预演阶段就能发现"主机名口径"带来的所有差异。
