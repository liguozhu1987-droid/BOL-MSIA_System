# 打包防杀软误报方法（BOL 管理系统）

> 本文件是与 `build_exe.ps1` 配套的方法论沉淀，用于后续把本系统（Django 后端 + Vue 前端 + SQL Server 双库）打包为 **Windows 可执行程序（exe）** 时，**系统性地规避杀毒软件误报与静默删除**，并把"打包看似成功但部署后白屏 / 接口 404"这类问题拦截在打包阶段。

---

## 0. 一句话结论

PyInstaller 产物被杀软误报，**首要原因是三件事：`onefile` 自解压、`UPX` 加壳、字节码加密/混淆**；再加上"无版本信息、无公司署名"的裸 exe 触发启发式扫描。因此本项目的打包基线固定为：

> **onedir 模式 + upx=False + block_cipher=None + 嵌入版本信息**，并在打包每个关键节点做"完整性闸门"以防杀软静默删除产物。

---

## 1. 防误报核心配置（每次打包都必须维持，不得改回）

对应文件 `backend/bol_server.spec`，四项关键约束已由 `build_exe.ps1` 步骤 0 自动校验，任何一项被改动都会让脚本直接中止：

| 约束 | 要求 | 为什么 |
|------|------|--------|
| **onedir 模式** | spec 中必须存在 `COLLECT(...)`，产物是 `exe + _internal/` 目录 | `--onefile` 单文件运行时会把自身解压到临时目录再执行，行为与恶意软件高度相似，是误报重灾区 |
| **upx=False** | `EXE(...)` 与 `COLLECT(...)` 中均 `upx=False` | UPX 是公开加壳器，恶意软件也用；加壳 = 杀软无法解包分析 = 直接判可疑 |
| **block_cipher=None** | spec 顶部保持 `block_cipher = None` | PyInstaller 的字节码加密/混淆同样让杀软无法静态分析，显著提高误报率 |
| **版本信息** | `EXE(..., version=str(SPEC_DIR / 'version_info.py'))` | 无版本信息、无公司署名的裸 exe 更易被判为"可疑程序" |

`version_info.py` 中已嵌入 `CompanyName` / `FileDescription` / `ProductName` / `LegalCopyright` 四类元数据。若日后版本升级，只需改 `version_info.py` 里的 `filevers` 元组（当前 `(2,3,0,0)`），**保持它是单个 `VSVersionInfo(...)` 表达式、不要加 docstring 或多余语句**，否则 PyInstaller 解析会失败。

### 另外两项隐性降低误报的手段

1. **`excludes` 精准裁剪**：spec 中排除了 scipy / numpy / pandas / PIL / matplotlib / django.contrib.gis / tkinter / pytest 等本系统用不到的大体积库。体积越小、依赖越"干净"，越不容易触发启发式。
2. **`hiddenimports` 显式声明**：django / rest_framework / waitress / openpyxl / apscheduler / email / mssql / pyodbc 及本地 `apps/*` 全部显式列出，避免运行时缺模块——这不是防误报本身，但能防止"打包后莫名 500"。

> **红线**：任何情况下都不要对 exe 或 `_internal` 目录做二次加壳、压缩、加密、混淆，也不要换成 `onefile`。

## 2. 打包流程与"完整性闸门"设计

`build_exe.ps1` 是唯一的执行入口，一键完成五步：

```
步骤0  前置检查         工具链 + spec/version_info 防误报配置自检（5 项断言）
步骤1  前端构建         vite build（可 -SkipFrontend 跳过）
闸门1  前端入口 JS 必须真实存在（防杀软静默删除 dist 产物）
步骤2  collectstatic     --clear 重新收集静态文件
闸门2  staticfiles 入口 JS 与前端 dist 完全一致 + 总数与三部分组成恰好相等
        （前端 dist + admin + rest_framework；Vite 8 产物约 60 个，合计约 214）
步骤3  PyInstaller 打包  onedir + 不加壳 + 不加密
闸门3  exe 生成且体积 > 5MB
步骤4  装配部署文件      放入 db_config.ini.example + 生成 README_DEPLOY.txt
闸门4  包内入口 JS / python312.dll+pyodbc / _internal\apps 完整
步骤5  生成 ZIP         .NET ZipArchive（正斜杠 + 目录条目 + Optimal）
闸门5  ZIP 无反斜杠 + 入口 JS>100KB + exe 大小一致
```

**设计动机**：本项目杀毒软件曾静默删除前端构建产物（入口 JS）与后端源码，导致"打包成功但部署后白屏 / 接口 404"。闸门把所有关键节点做真值校验（文件真实存在 + 体积合理 + 前后一致），把杀软删文件问题拦截在打包阶段，而不是部署之后才暴露。

### 使用方式

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_exe.ps1            # 完整流程
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_exe.ps1 -SkipFrontend  # 前端未改动，跳过构建
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_exe.ps1 -NoZip          # 只打包不压缩，便于本地冒烟
powershell -NoProfile -ExecutionPolicy Bypass -File .\build_exe.ps1 -IncludeDbConfig # 连本机 db_config.ini 一起打包（跨机慎用）
```

> **两个脚本执行陷阱（踩过实坑）**：
> 1. 必须用 `-NoProfile` + `ExecutionPolicy Bypass` 启动，否则受执行策略限制。
> 2. 脚本内部用 `Invoke-Native` 包装 npm/python：因为 vite、PyInstaller 会把 INFO/警告写到 stderr，若脚本全局 `$ErrorActionPreference='Stop'` 会触发 `NativeCommandError` 假失败。`Invoke-Native` 临时切 `Continue` 收集输出、改用 `$LASTEXITCODE` 判成败。

## 3. DRF `@action` 路由规范（防止 404）

这是本项目踩过的第二个真实坑：10/8 重构中多个 `@action` 漏写 `url_path`，DRF 默认按方法名生成 **下划线** 路由（`filter_options/`），而前端调用 **连字符**（`filter-options/`），导致 404。

**规范**：所有 `@action` 必须显式写 `url_path`，且与前端约定一致（本项目统一连字符）：

```python
# backend/apps/budget_bol/views.py（已修复）
@action(detail=False, methods=['get'],  url_path='filter-options')   # 原 filter_options
@action(detail=False, methods=['post'], url_path='import-excel')     # 原 import_excel
@action(detail=False, methods=['get'],  url_path='import-logs')      # 原 import_logs
@action(detail=False, methods=['post'], url_path='clear-all',
        permission_classes=[IsAdmin])                                # 原 clear_all
```

**打包后必须冒烟验证的自定义路由**：`filter-options` / `import-logs` / `import-template`（应 200）、`clear-all`（非管理员应 403/401）。

## 4. ODBC 驱动注意事项（防止接口全部 500）

本系统连接 SQL Server，接口全部依赖 ODBC 驱动。**驱动不匹配是"登录/接口全部 500"的第一嫌疑**：

| 症状 | 根因 |
|------|------|
| 登录/接口全部 500，空响应体 | db_config.ini 里 `driver` 与目标机器实际安装的驱动不符 → `IM002 [Microsoft][ODBC Driver Manager] Data source name not found` |
| 打包后好的包，重打包后突然 500 | 打包时 dist 被清空，误把"参考包"的 Driver 18 配置复制进来，而本机只装 Driver 17 |

**规范**：
1. 目标机器先查实际驱动：`Get-OdbcDriver | Select-Object Name`（常见 `ODBC Driver 17 for SQL Server` / `ODBC Driver 18 for SQL Server`）。
2. `db_config.ini` 的 `driver` 必须与之一字不差。
3. `build_exe.ps1` **默认不带 `db_config.ini`**，只放 `db_config.ini.example`（环境相关配置不随包分发，避免目标机驱动不匹配）。仅本地冒烟时可用 `-IncludeDbConfig`。
4. 不建 `db_config.ini` 时，程序用内置默认值（Driver 18），但内置默认不含数据库口令，必须先创建配置才能连接数据库。

## 5. 杀毒软件白名单 / 排除项指南

根本性地降低误报，靠的是**白名单 + 签名**，配置/代码做到位只是降低"概率"：

1. **最有效**：把部署目录加入杀软"排除项/白名单"。Windows Defender 路径：`Windows 安全中心 → 病毒和威胁防护 → 排除项 → 添加或删除排除项`，添加 exe 所在整个目录（含 `_internal`）。
2. **实时防护干扰打包**：打包过程中若 `backend\dist` 或 `frontend\dist` 被实时查杀，把这两个目录也加入排除项后重新执行。
3. **正式交付**：若公司有代码签名证书，对 `BOLServer.exe` 签名可大幅消除 SmartScreen/杀软告警；已签名则无需再逐台加白名单。
4. **交付前验证**：用 VirusTotal 扫一遍 exe 确认未被标记（注意：上传到 VirusTotal 会公开哈希，内部系统需谨慎评估合规）。
5. 不要对 exe / `_internal` 做二次加壳、压缩、加密（同第 1 节红线）。

## 6. 文件被杀软删除后的恢复手册

当发现源文件或构建产物"凭空消失"，按以下顺序找回——**先找回源文件，再重新打包，切勿直接重装/重建**。

### 6.1 前端源文件 / 构建产物

- **症状**：`index.html` 引用的 `assets/index-XXXX.js` 不存在，或源文件 `frontend/src/api/index.js` 消失 → 白屏。
- **恢复源文件**：VS Code 本地历史
  - 路径模式：`C:\Users\<用户>\AppData\Roaming\Code\User\History\<8位hex优先>\<随机名>.js`
  - 本项目曾从 `History\-9d2e483\MJoL.js` 恢复 `frontend/src/api/index.js`（10/7 版本）。
  - 方法：在该 `History` 目录按文件名搜索，取时间正确的最新一份。
- **恢复后在杀软隔离区确认**：Windows Defender `病毒和威胁防护 → 保护历史记录` 中把被隔离文件"还原"+ 加白名单，否则还会再删。

### 6.2 后端源码文件（.py）

本项目后端也发生过 `views.py` 部分 action、`models.py` 被杀软删除。恢复优先级：

1. **VS Code 本地历史**（同上，最快）。
2. **已打包产物逆向**：从 `dist/BOLServer/_internal` 里的 `base_library.zip` / `*.pyc` 提取：
   - 用 `pyinstxtractor.py` 解出 `.pyc`。
   - 用 `pyi-archive_viewer`（PyInstaller 自带）或直接解 `base_library.zip` 拿 `.pyc`。
   - 用反编译工具（本项目保留了 `pycdc-master` 工具链于 `_extract\recovery`）把 `.pyc` 还原为 `.py`，必要时手工补丁。
3. **运行时 `_meta` 精确重建**：对 `models.py` 这类字段定义，若逆向失败，可依据 `python manage.py check` 的报错逐字段重建模型（本项目 `apps/actual_ct/models.py` 即用此法恢复，`apps/analytics/views.py` 用 pycdc 补丁 + legacy pyc 落位恢复）。
4. **回收站**：最后兜底（杀软"静默删除"通常不进回收站，但手动误删会进）。

> 恢复完成后务必 `python manage.py check` 通过，再走 `build_exe.ps1` 重新打包 + 冒烟测试。

### 6.3 冒烟测试（打包后必做）

```powershell
Start-Process '.\backend\dist\BOLServer\BOLServer.exe' -WorkingDirectory '.\backend\dist\BOLServer'
Invoke-WebRequest  http://127.0.0.1:8090/ -UseBasicParsing                      # 期望 200（页面不白屏）
Invoke-RestMethod http://127.0.0.1:8090/api/auth/guest-login/ -Method POST      # 期望 200
```
- 登录返回 **500** → 优先查 `db_config.ini` 的 driver（第 4 节）。
- 页面 **200 但白屏** → 查包内 `_internal\staticfiles` 的入口 JS 是否被杀软删除（闸门 4/5 会拦截）。
- 打包前若有旧 `BOLServer.exe` 僵尸进程占用 8090，先 `Stop-Process -Name BOLServer -Force`（脚本步骤 0 已自动处理）。
